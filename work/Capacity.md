# NACP 与四传输：短时上界探索

2026-10-09；i5-12600，Node.js 24.19.0。未限 CPU 核数，为前期探索；最终限核长时间实验由用户执行。

## NACP 理论预算

协议本身没有一个固定 msg/s 上限。给定客户端/服务端算力、链路有效带宽、并发和 RTT，容量受到最小瓶颈约束：

`R ≤ min(R_client, R_server, B_up / bytes_up, B_down / bytes_down, in_flight / RTT)`

下面预算使用当前 CBOR 信封和 NACT 32 字节头，echo 一次调用：Request、Response、两条 ACK。没有包括 TCP/IP、HTTP、WebSocket 外部封装和重发，按默认单帧计算。

| 业务载荷 | Request | Response | 两条 ACK | 每次双向总字节 | 双向业务字节占比 |
|---|---:|---:|---:|---:|---:|
| 256 B | 480 B | 526 B | 412 B | 1,418 B | 36.11% |
| 64 KiB | 65,762 B | 65,810 B | 412 B | 131,984 B | 99.31% |
| 1 MiB | 1,048,802 B | 1,048,850 B | 412 B | 2,098,064 B | 99.96% |

以每方向 1 Gbit/s、无其他开销为例，链路数学上界分别约 170,765 / 1,893 / 119 次 echo/s，取两个方向中较大的每次字节成本（Response + Request ACK）。这不是本机 TCP 回环带宽，也不是实际网络性能承诺。

## NACP 无网络处理参考上界

两个 NApp 在同一进程，消息用 queueMicrotask 直接交给 NACP，真实执行注册、请求关联、ACK、能力调度、响应；旁路 NACT 分帧、CBOR 和 socket。echo 数据按引用传递，不复制，客户端逐字节比对。此项包含两个端点的 JS 开销，不能与双进程结果做严格成本相减。

3 秒测量、2 秒预热、1/4/16/64 在途扫描：

| 载荷 | 观察到的峰值调用/s | P99 | 相应无网络阶段 RSS（合并进程） |
|---|---:|---:|---:|
| 256 B | 31,244 | 0.044 ms | 294 MiB |
| 64 KiB | 29,527 | 0.050 ms | 434 MiB |
| 1 MiB | 19,661 | 0.155 ms | 396 MiB |

64 KiB 路径对应每次约 33.9 微秒的组合处理成本；这是这台机器/实现/实验的经验参考上界，不是协议理论证明。1 MiB 无网络“MiB/s”按引用回显计算，不代表搬运了这些字节。没有声称 NACAB、NACEB 所有业务形态具有相同容量。

## 四种真实传输

一个客户端进程包含 4 个 NApp，服务端独立进程；真实 NACT/CBOR/NACP。每级 3 秒，持续复用连接，无重建；每连接在途扫描 1/4/16/64，1 MiB 的最高级限到 16（总载荷≤64 MiB）。以下只取该短扫描观察到的最大完成率，不是长期可持续容量。

| Provider | 256 B 峰值/s | 64 KiB 峰值/s | 64 KiB 双向有效 MiB/s | 1 MiB 峰值/s | 1 MiB 双向有效 MiB/s |
|---|---:|---:|---:|---:|---:|
| Unix socket | 19,214 | 8,834 | 1,104 | 803 | 1,606 |
| TCP socket（原始） | 2,808 | 8,033 | 1,004 | 813 | 1,627 |
| HTTP Stream | 1,097 | 668 | 83.6 | 94 | 187 |
| WebSocket | 15,519 | 4,436 | 554 | 400 | 800 |

256 B TCP 原始值依赖 256 总在途。低并发仍受 Nagle/延迟 ACK 限制；测试包装层 NODELAY 对照把 256 B 峰值提高到约 16,477/s。64 KiB NODELAY 约 7,631/s，1 MiB 约 830/s，无明显数量级变化。正式 Provider 没有改动。

64 KiB 吞吐相对无网络参考上界约 Unix 29.9%、TCP 27.2%、WebSocket 15.0%、HTTP 2.3%。这些比率包括编码、分帧、传输、JS调度、GC和验证，不能解释为某传输独立占用了剩余百分比。发压端本身会饱和，还没有测多发压进程下服务端独立极限。

## 内存与延迟边界

| Provider | 64 KiB 峰值阶段 P99 | Client RSS / Server RSS | Client ArrayBuffer / Server ArrayBuffer |
|---|---:|---:|---:|
| Unix | 13.82 ms | 464 / 390 MiB | 83 / 82 MiB |
| TCP | 16.24 ms | 472 / 284 MiB | 80 / 60 MiB |
| HTTP Stream | 122.36 ms | 505 / 271 MiB | 73 / 21 MiB |
| WebSocket | 23.31 ms | 570 / 344 MiB | 136 / 34 MiB |

客户端跨路径复用，RSS 包含前阶段内存保留，不是该 Provider 独立净开销。上表是绝对峰值，完整结果同时保存 heap、ArrayBuffer、起始/结束 RSS 与每秒采样。

- Unix 1 MiB 并发64（4连接×16）阶段双进程 RSS 554/501 MiB，P99 103.68 ms。
- HTTP 1 MiB 4连接×16：约92/s，P99 725 ms、Client RSS 620 MiB；增加并发并没有提高吞吐。
- 更早 HTTP 1 MiB 4连接×64 边界探索：0次成功，256调用在阶段收尾超时后失败，Client RSS约704 MiB。这次失败已单独留存上报，不能纳入有效吞吐。
- 降载5秒后 RSS仍未完全下降，例如HTTP客户端约604 MiB。这可以是分配器/GC保留或仍存活对象，短时观察不能判定泄漏。需要限核长期稳态、排空与恢复阶段确认。

最初固定到达率探索受runner调度和在途cap限制（尤其无网络cap=1每毫秒一批）；该组不能作为容量平衡判据。后续改为无网络每拍yield并增加固定到达率在途headroom，最终平衡点须由限核长实验确认。
